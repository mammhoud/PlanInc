# Internationalisation (PI-009)

> Part of **PlanInc** — AI-powered card note-taking and planning

The active locale tree is `frontend/public/locales/<lang>/`. It is bundled by
the Vite build and served by the root `server/` process. `frontend/dist/` holds a
gitignored build copy of the same trees; never edit it by hand.

## Locale set

`ar`, `de`, `en`, `es`, `fr`, `ja`, `ka`, `kab`, `ko`, `nl`, `pl`, `pt`, `ru`,
`tr`, `uk`, `zh`, `zh-TW`.

`en` is the **reference set**. Every other locale is measured against it: a
locale may not invent keys, and every reference key must be present. Deviations
from the reference key set are a bug, not a translation choice.

## How lookups work

The frontend i18n layer holds the lookup code and locale files. A missing key
falls back to the reference locale rather than
rendering the raw key, which is why a missing translation is easy to miss in the
UI and why parity is enforced by a check instead.

```ts
// frontend/src/lib/i18n.ts — fallbackLng: 'en', loadPath: '/locales/{{lng}}/{{ns}}.json'
i18n.t("some.key", { lng: "de" });
```

Two rendering paths matter, and both are covered by the check:

- **Coverage** — the key exists at all. A key that is absent from `en` renders
  as the raw key for English users, so a code path calling `t('update-failed-generic')`
  was silently broken until that key was added to the reference set.
- **Translation** — the key exists but still holds the English text. i18next
  returns it happily, so an untranslated label and a translated label are
  indistinguishable at runtime. Only the check tells them apart.

## Parity and completeness are checked, not hoped for

`projects/scripts/i18n_translate.py --check --target planinc-frontend` is the
gate. It reports, per locale, the key count, the number of values still
identical to the reference, keys missing from the locale, and keys the locale
defines that the reference does not.

```bash
# from the monorepo root
python3 projects/scripts/i18n_translate.py --check --target planinc-frontend
```

Missing keys and untranslated values are separate defects and are fixed
separately: `--apply` translates the gaps, and `--prune-extra` deletes the
locale-only keys.

Why key uniqueness still matters even though JSON cannot express a duplicate
key: `JSON.parse` keeps the **last** occurrence silently, exactly like the object
literal that once declared `viewRecycle` and `viewArchive` twice in
`frontend/i18n.mjs`. The later declaration won, so the live-filter group's
`'Bin'` silently overwrote the toolbar's `'Recycle bin'`. That loader is gone —
the locale bundles are JSON now, where the same failure mode shows up as a
duplicated key in the file, which the JSON parser hides and a diff does not.

## Adding a language

1. Create `frontend/public/locales/<code>/translation.json`.
2. Copy the reference (`en`) key set — do not invent keys.
3. Add the code wherever locales are enumerated, including the language switcher.
4. Run the check above. A missing key fails it, so this step is not optional.

## Adding a string

1. Add the key to `frontend/public/locales/en/translation.json`.
2. Fill it for every other locale — either by hand in each
   `translation.json`, or through the shared tool:

   ```bash
   GOOGLE_API_KEY=... python3 projects/scripts/i18n_translate.py \
     --apply --target planinc-frontend --only de,fr
   ```

3. Use `i18n.t(...)` in `frontend/` — never a literal in the markup. Dynamic
   lookups such as `t(\`share-scope-${scope}\`)` are fine, but every value that
   can reach the call site has to exist in the reference set.
4. Re-run the check. It fails on a missing key, so this step is not optional.

> When adding a key, check the site that renders it for a duplicate name.
> A duplicate key in the same JSON object is legal and the last one silently
> wins; a diff is what turns that into a visible mistake.
